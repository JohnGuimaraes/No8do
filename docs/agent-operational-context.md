# Agent Operational Context

Operational Context is a replaceable, session-scoped snapshot of untrusted operational signals. It is separate from the persistent administrative assignments (`AgentProjectAssignment`, `AgentWorkItemAssignment`, and `AgentConnectionAssignment`) and grants no access or authority.

`Signal` (canonical repository identity, branch, repository-relative working directory, and bounded references) is not `Resolution`. In 3D.14, only a canonical `GIT` / `github` / `github.com` repository is resolved through the Workspace's GitHub App installation. The provider's numeric repository ID is persisted as an opaque string per session; clone URLs and provider payloads are not stored.

The GitHub lookup uses the fixed `api.github.com` origin and a temporary installation token for the effective Workspace derived from the AgentSession (bound sessions use Agent → Workspace; legacy sessions use their stored workspace). `workspaceHint`, repository owner, and GitHub login never select authority. Custom hosts (including GHES) and other providers are unsupported and cause no outbound request.

Project association lookup is local and always scoped to that same Workspace. Zero associated Projects yields `UNRESOLVED`; one yields `RESOLVED` with `HIGH` confidence; multiple yield `AMBIGUOUS` without choosing a winner or exposing candidate IDs. Archived Projects remain eligible because this records association, not permission. A repository rename/transfer triggers lookup by the new locator; if GitHub returns the same stable numeric ID, the existing Project association still resolves.

An unchanged canonical repository identity reuses its session-persisted provider ID when branch, working directory, or references change; those updates do not call GitHub again and can recalculate the local association. A changed repository performs a new provider lookup. Removing the repository clears its provider ID and Project resolution. GitHub 404/inaccessible is a safe negative result; a supported GitHub signal without an effective Workspace, missing installation/configuration, authentication, rate-limit, server, timeout, and network errors fail the PUT operationally and do not persist a false resolution.

The initial provider request runs outside a database transaction and AgentSession lock. A short write transaction rechecks the session context version and signal hash before atomically saving the signal and resolution; stale concurrent results return conflict. Project repository association create/change/dissociate and Project deletion trigger post-commit, same-Workspace local refresh by the persisted provider ID. The Project FK's `ON DELETE SET NULL` is also normalized to `UNRESOLVED`, so no response can expose `RESOLVED` with a null Project ID.

The snapshot is independent of Agent lifecycle, AgentSession heartbeat/presence, Runtime Mode, capabilities, policies, and assignments. A context PUT never changes those domains. Workspace authority comes from the session owner and, for a bound session, the backend-derived `AgentCredential → Agent → Workspace` chain. An optional workspace hint is consistency-only and is not stored.

`PUT /api/agent-sessions/{sessionId}/operational-context` replaces the whole signal and is separate from heartbeat. Canonically identical signals are no-ops; changed signals advance the version. GET returns the current snapshot; a legacy session without one returns 404 and is not backfilled. Disconnected or revoked sessions cannot be updated; revoked sessions cannot read it. Existing snapshots remain stored after disconnection.

Repository fields are structured canonical identity, never a raw clone URL. Working directories must be repository-relative and are normalized to `/`. References are bounded typed identifiers, not arbitrary URLs. Responses and `AGENT_OPERATIONAL_CONTEXT_CHANGED` events omit credentials, fingerprints, raw URLs, repository locator values, and ambiguous candidate IDs; event metadata contains version, fixed changed-field labels, resolution statuses, the unique resolved Project ID when present, and controlled evidence code. Resolution does not create, update, or remove administrative assignments; it does not alter Agent lifecycle, capabilities, policies, Runtime Mode, or authorization. Work Item remains `UNRESOLVED`.

Operational-context events remain excluded from the generic Agent audit trail. A dedicated audit record for material Project-resolution transitions is deferred to avoid enabling generic branch/cwd/reference audit volume; no Project Activity is created by resolution.

The future No8do Integration Plugin is responsible for converting local Git remote forms into canonical identity before sending them. Backend validation remains mandatory. This phase adds no plugin, MCP/Gateway integration, Area, or assignment behavior. GHES and all non-GitHub providers remain deferred.
